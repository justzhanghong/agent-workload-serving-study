# 主实验边界：必须是多轮Agent负载

研究目标是在多轮Coding / Work Agent负载中找出服务端瓶颈，为decode芯片设计提供依据。“HBM带宽比计算更值得优先投入”只是候选假说，不是预定结论；也不能让它代替对其他瓶颈的调查。

主实验可用AgentX公开轨迹或真实任务数据，但必须保留同一会话中的多次模型调用、历史/前缀关系、上下文变化及各轮输出工作量。单轮算子、随机历史和强制固定输出token只作解释机制的辅助诊断；任何资源投入建议都必须回到相同的多轮负载验证。

## 本轮先用AgentX

从此前固定的256个会话、2048次请求中，按预先固定的等间隔索引选择64个会话，每个保留前8次调用，共512次；不是只抽512个独立请求，也不是每个原始长会话的全部调用。冻结完整请求文件、原始文件及清单指纹，所有对照使用同一批会话窗口，不按性能结果挑选样本。

| 项目 | 约束 |
|---|---|
| 模型与硬件 | 先用DeepSeek-V4.1-Flash，B200×4、TP4/EP4，正常前缀缓存；不做PD |
| 会话依赖 | 每个root的前8次调用严格串行，前一次输出完成后才能发送下一次；不同root并发 |
| 分支 | 保留既有AgentX清单的分支/子调用及顺序；同root内串行，不称为真实子Agent并行执行 |
| 输出 | 每条使用轨迹记录的不同输出长度，总输出预算443423 token；原始0按接口要求升为1，不统一为1/32/256，也不限制生成内容 |
| 历史 | 使用既有冻结回放输入；不人工预建一个目标长度的随机历史，不追逐缓存命中目标 |
| 测量起点 | 从每个会话第一条调用开始计入，首轮与后续轮次分开统计；跨会话自然共享前缀可以命中 |
| 初态 | 每个配置启动全新服务，不复用前一配置KV；保留全部所选调用 |
| 并发 | C16与C56；max-num-seqs=256，C表示最多活跃会话窗口，不当作实际decode batch |
| 上下文 | 服务上限1048576，所选源数据最大prompt＋output为201872；源长度筛选跳过0条，服务端仍核对实际usage |
| 重复 | 计划3次独立重复，交错配置顺序；未完成和受同卡其他任务干扰的运行不冒充有效重复 |

该清单是既有AgentX的连续轨迹回放，不执行工具，也没有可核验的真实工具等待。本阶段不把请求起始时间差当作工具耗时，不将它称为真实自主任务闭环。输入来自冻结轨迹，当前新生成的响应不会替换原轨迹历史；实际缓存命中必须测量，不能保证生成历史全部复用。真实任务轨迹的等待/暂停恢复是后续单独一组，不能拿本组连续回放外推。

## 问题先于资源投入结论

| 候选瓶颈 | 多轮负载中需找的证据 | 不能直接推出 |
|---|---|---|
| KV/专家权重访问 | 首轮后实际未缓存量、历史长度与实际B下的decode时间；后续补真实流量/带宽证据 | 高命中率不等于decode不再读历史；逻辑字节不等于实测HBM瓶颈 |
| 增量prefill与decode相互干扰 | 后续轮次返回时的mixed/pure-decode迭代、排队、TTFT/TPOT变化 | 全部慢迭代不能一概归为decode算力不足 |
| 轮间状态与容量 | 轮次/分支变化、命中变化、KV块及驱逐/重算证据 | 命中下降不自动等于容量不足，已分配块也不等于全部保留状态 |
| mHC/索引/小矩阵/通信/供给 | 多轮回放中的算子及设备/宿主时间，必要时再抽样profile | 单轮profile的累计时长不能直接成为多轮占比或互连瓶颈结论 |

先以C16/C56参考核心频率建立阶段、轮次和实际B的观测，再加入C56低核心频率的诊断对照。参考组请求1965 MHz，低频组请求1200 MHz，实际生效频率以逐秒遥测为准，不把请求值当成实测值。这个干预同时影响B200上的prefill和decode及其他核心路径，不独立改变Tensor Core吞吐；无PD时不能把端到端变化全部算成D芯片收益。没有生效的HBM干预，就不报告HBM与计算的投入优先级。

## 输出与证据门槛

- 主要指标来自整个8次调用窗口：逐轮TTFT/TPOT、请求SLA通过率、SLA内输出goodput、窗口完成时间及运行间范围。
- 分开首轮和后续轮次，按缓存/未缓存输入、分支和长度分组；C16/C56比较使用同一批窗口，不与原2048条结果混成重复。
- 联合后端每迭代真实context/generation批次与elapsed_ms，并抽样记录调度器逻辑上下文；异步bookkeeping不当作硬件流量计数器。
- 客户端仅能核验SSE输出chunk时，报告chunk gap而不是单token ITL；不从请求平均TPOT反推出P99 ITL。
- 细粒度profile另开诊断运行，不把采样扰动混入正式吞吐/SLA；任何算子改动须回到完整多轮回放复验。
- 结论必须注明多轮阶段、并发、长度/缓存条件与B200平台。无证据时保留“未验证”，不为了验证假说而强行选择支持它的数据。

执行状态必须区分“清单/脚本准备完成”“等待GPU”“回放进行中”“核验完成”。GPU被其他任务使用时等待；不得共享GPU测速度，不因排队脚本已启动就写成实验完成。
